# M1 — Trace dissection: where do the tokens go?

Course base: W1 (trace dissection). Capture Claude Code and pi through mitmproxy, then account for every token:
system prompt, tool schemas, tool results, cache reads/writes.

## Setup (2026-11-09)
- mitmproxy 11.0.2 via `uv tool install mitmproxy` (isolated venv).
- `tracer/run.sh <label> <cmd...>`: starts `mitmdump` on 127.0.0.1:18080 with `tracer/capture.py`, runs the command with
  `HTTPS_PROXY` + `NODE_EXTRA_CA_CERTS`. **CA trusted only by that child process**, never by the system keychain.
- `tracer/capture.py` writes redacted JSONL (auth headers, cookies, token/secret JSON keys) to `traces/DATE/label.jsonl`.
  No `-w` flows file: raw flows would contain credentials. SSE is streamed through live and teed, then reassembled into
  the final message.
- `tracer/report.py summary|dump`: per-request breakdown (chars/4 estimates per component; exact totals from `usage`),
  and a markdown dump of one request (system blocks, tools, messages, response).
- Verified: no `sk-ant-`, `Bearer`, or token values in the trace or mitm log.

## First capture: `claude -p "Reply with just: hi"` (Claude Code 2.1.285, Opus 5.5)
- **21 HTTP flows for a one-word answer**, only 1 is `/v1/messages`. The rest: MCP registry (4×, ~220KB each),
  OAuth org/account lookups, feature flags (`grove`, `penguin_mode`, `bootstrap`), connected MCP servers via
  `mcp-proxy.anthropic.com`, event logging (one batch ~400KB), Datadog logs.
- The one model call: **~17k input tokens to say "hi"**: `cache_read=8368`, `cache_write=8666` (all 1h TTL), `input=2`, `output=4`.
- Request layout:
  - `system[0]`: billing header as text (`cc_version`, entrypoint, prompt id); `system[1]`: "You are a Claude agent, built on the Agent SDK" (because `-p`)
  - `system[2]`: core prompt, `cache_control {ttl: 1h, scope: global}`. **Global scope** = shared across users,
    which is likely why even the first call reads ~8.4k from cache.
  - `system[3]`: session-specific part (1h TTL).
  - 12 tools ≈ 5.5k est. tokens; the rest are **deferred** behind `ToolSearch` (names only, schemas on demand).
  - A mid-conversation `system`-role message (~4.3k est.) carrying environment/skills/agents context, cached.
- Other fields: `thinking: adaptive` (display omitted), `context_management: clear_thinking`, `output_config.effort: medium`,
  `thread`, `diagnostics.previous_message_id`, `max_tokens: 128000`; 18 `anthropic-beta` flags.
- chars/4 undercounts (≈12k est. vs 17k real); JSON tool schemas tokenize denser than prose. Use `count_tokens` for exact per-component numbers.

## Version diff: Claude Code 2.1.285 → 2.1.311 (same `-p` prompt, `tracer/report.py diff`)
- Input **17.0k → 18.0k tokens** (cache_read 8368→9013, cache_write 8666→8948): ~+5% context for a no-op prompt in 26 releases.
- Same 12 tools, same request fields. Tool descriptions grew: Agent 829→1027 est. (fork subagents, background-by-default text),
  Bash 844→955, Read 417→501.
- Beta flag `mid-conversation-system-2026-04-07` dropped (the system-role message is still sent; presumably folded into GA).
- Prompt changes are mostly safety/behavior text: a longer `<pasted_content>` rule (act on a pure paste; embedded instructions in
  docs/logs aren't requests), a new rule that downloaded files are untrusted (separate dirs, `python -I`, planted `json.py`),
  `/code-review` gained `--max-findings` and "never use max/ultra on your own judgment".
- Model list in the environment block: Haiku 4.5 → **Haiku 5.5** (`claude-haiku-5-5`). The prompt is also a release-notes channel.
- Takeaway for the harness: a frontier client's fixed prefix drifts upward release over release; it is all cached, so the
  cost is mostly cache writes (1h TTL: 2× base input price) on each new session or version.

## Caveats
- `-p` runs as the SDK entrypoint (`sdk-cli`), so its prompt differs from the interactive CLI. Capture interactive sessions too.
- The proxy changes networking only; the client is the same binary with the same flags.
