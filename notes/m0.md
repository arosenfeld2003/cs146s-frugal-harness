## Benchmarks
Mac M4 Pro (llama.cpp build 12110 via brew). `gpu` = Metal, all layers; `cpu4` = `-ngl 0 -t 4` (VPS proxy, upper bound).

| model | file | mode | pp512 t/s | tg128 t/s |
|---|---|---|---|---|
| Qwen3.5-2B | Q4_K_M 1.28GB | gpu | 1981 | 132 |
| Qwen3.5-2B | Q4_K_M 1.28GB | cpu4 | 140 | 56 |
| Qwen3.5-4B | Q4_K_M 2.74GB | gpu | 781 | 62 |
| Qwen3.5-4B | Q4_K_M 2.74GB | cpu4 | **58** | 26 |
| Gemma-4-E4B (Google QAT) | q4_0 5.15GB | gpu | 1324 | 65 |
| Gemma-4-E4B (Google QAT) | q4_0 5.15GB | cpu4 | **188** | 41 |

Takeaway so far: on CPU, **prompt processing** (~140 t/s) is the bottleneck, not generation.
A 4k-token log ≈ 30s just to read → sidecar inputs must be short or chunked.

Surprise: the biggest file (Gemma E4B, 5.15GB) reads prompts **3× faster on CPU** than Qwen3.5-4B (188 vs 58 t/s),
and faster than the 2B. Confounded: different quant formats (q4_0 has well-optimized ARM CPU kernels; Q4_K_M is heavier),
and different architectures (Gemma E4B's per-layer embeddings → ~4B "effective" compute). Hypotheses, not conclusions.
**M6 follow-up:** bench Qwen3.5-4B **Q4_0** to separate quant effect from architecture. File size ≠ speed.
Speed is only half the story — quality on sidecar tasks (M3) decides the winner.
